# 資料庫並發控制技術規範 (Optimistic vs Pessimistic Locking)

## 1. 背景與目的
在醫院 HIS 系統重構任務中，為確保多位醫師/護理師同時修改同一筆臨床資料（如醫囑、護理紀錄）時，不會發生「後蓋前」的資料遺失問題 (Lost Update)，特此進行並發控制 (Concurrency Control) 技術評估。

## 2. 技術方案比較

### A. 樂觀鎖 (Optimistic Locking) - 推薦方案
*   **原理**：不實際鎖定資料，而是透過「版本號 (Version)」機制進行檢查。
*   **語法實作**：
    ```sql
    UPDATE locking_test 
    SET order_content = ?, version = version + 1 
    WHERE id = ? AND version = ?;
    ```
*   **優點**：
    1.  **效能高**：不會長時間佔用資料庫連線。
    2.  **併發能力強**：允許多人同時閱讀、編輯。
*   **缺點**：如果衝突頻繁，醫師在存檔時才被告知失敗，體驗較差。
*   **適用場景**：**醫師病歷修改、醫囑錄入**（衝突機率低、編輯時間長）。

### B. 悲觀鎖 (Pessimistic Locking)
*   **原理**：利用資料庫原生的鎖定機制 (`FOR UPDATE`)，在讀取時即霸佔資料。
*   **語法實作**：
    ```sql
    SELECT * FROM locking_test WHERE id = ? FOR UPDATE;
    ```
*   **優點**：絕對保證資料一致性，且不會有「存檔失敗」的情況（因為別人進不來）。
*   **缺點**：
    1.  **連線耗盡風險**：若使用者點開畫面後不按儲存，連線會被一直佔用。
    2.  **不適用 Web**：Web 請求完成即斷開，難以維持長期的資料庫鎖。
*   **適用場景**：**藥局撥藥扣庫存、床位掛號預約**（操作時間極短、絕對不能衝突）。

## 3. 重構建議
1.  **優先採用樂觀鎖**：針對絕大多數的臨床紀錄，應於各資料表增加 `version` 欄位。
2.  **隱藏欄位設計**：在 JSP 表單中，必須使用 `<input type="hidden">` 攜帶版本號。
3.  **衝突處理**：當 `executeUpdate()` 回傳為 0 時，系統應明確提示「資料已被他人修改」，並提供重新整理功能。

## 4. 實驗紀錄 (POC Result)
*   **樂觀鎖**：成功演示醫師 B 先更新後，醫師 A 因版本不符導致更新失敗。
*   **悲觀鎖**：於 Java 單機環境成功演示醫師 A 必須等待醫師 B 提交事務後方可讀取。
